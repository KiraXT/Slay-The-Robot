# 整体美术风格、UI 与交互优化设计

## 背景

本次评审以现有 Godot 工程为基础，目标是让游戏交互整体贴近《杀戮尖塔》的清晰、稳定、低学习成本体验，同时让视觉风格转向二次元角色魅力和《弹射世界》式明快、模块化、轻快反馈。当前工程已经具备较好的战斗交互骨架：卡牌拖拽、轨迹线、目标高亮、卡牌释放动画、命中停顿、屏幕震动、程序化 VFX/SFX 和数据驱动卡牌表现字段已经存在。标题与选角界面也已经有分层舞台、视差、角色切换和可跳过转场。

当前主要问题不是单纯缺少美术资源，而是资源和 UI 规范没有形成统一系统：卡图、角色、敌人、事件、图标和弹层各自有质量基础，但风格密度、导出规格和展示方式不一致。继续按单张图逐项美化会产生高返工，因此本设计采用“系统外壳先统一，内容资产按角色链路小批量修正”的低迭代成本路线。

## 目标

1. 保留现有《杀戮尖塔》式交互骨架：顶部资源区、中部战斗区、底部手牌、路径地图、奖励/商店/牌库弹层和清晰回合反馈。
2. 将整体视觉统一为“二次元角色核心 + 弹射世界式明快 UI + 轻机械浮岛世界观”。
3. 优先修正会直接破坏观感的资产契约问题，例如角色绿底、透明通道、尺寸规格、缩略图可读性和缺图 fallback。
4. 使用 UI 外壳、描边、底座、遮罩、程序化 VFX 和数据字段统一观感，减少全量重画需求。
5. 把美术生产从“单图出图”改为“角色链路/内容链路出图”：一个角色一次统一立绘、头像、能量图标、共用卡图和高频卡图。
6. 让后续新增资源有明确验收标准：真实游戏尺寸、透明通道、构图安全区、小尺寸辨识度、色彩和风格版本。

## 非目标

1. 不全量重绘 92 张卡牌、所有敌人、所有事件图和所有 UI。
2. 不改变卡牌战斗逻辑、敌人行为、地图生成、奖励规则或数据驱动架构。
3. 不复制《杀戮尖塔》或《弹射世界》的具体素材、角色、图标、字体或受保护界面。
4. 不将机器人高细节写实风作为主视觉；机器人元素只作为世界观细节和敌方设计来源。
5. 不在第一阶段引入复杂逐帧动画系统。首阶段继续以静态图、Tween、程序化 VFX 和少量粒子为主。
6. 不为每张卡制作独立动效图；卡牌表现通过 `card_visual_profile`、`card_play_sfx`、`card_impact_vfx`、`card_screen_shake` 和 `card_hit_pause` 等字段复用。

## 当前现状判断

### 交互骨架

`scripts/ui/Hand.gd` 已经实现手牌扇形排列、悬停放大、拖拽出牌、曲线轨迹、目标高亮、无效摇动反馈和打出收束动画。这个基础应继续保留，并在视觉层增强箭头、目标框、卡牌释放节奏和不可用状态，而不是重写交互。

`scripts/ui/CombatFeedbackPresenter.gd` 已经集中处理命中闪烁、屏幕震动、hit pause、SFX、牌堆反馈和程序化命中特效。后续所有战斗手感优化应优先接入这个表现层。

地图已经按《杀戮尖塔》方向引入起点、层级路线和虚线连接，路线阅读方向正确。后续重点是地图图标、路径强调和可选/不可选状态。

### UI 外壳

`scenes/ui/Card.tscn` 已经采用亮色模块卡框，卡名、卡图、类型、描述和星级分区明确，适合继续作为全局卡牌模板基准。

多处弹层仍是浅青遮罩加白色矩形容器，包括奖励、商店、牌库、地图、暂停和事件对话。信息可读但工程感较强，需要统一为弹射世界式明亮面板：白底、青蓝描边、橙色主操作、深色正文、轻阴影、短节奏弹入弹出。

### 内容资产

角色和卡图已经偏二次元审美，事件图也有较强角色魅力和机械场景表现。敌人资产质量不低，但存在高细节机械怪和扁平方块图标混用的问题。遗物和状态图标更接近当前推荐方向，可以作为图标系统参考。

角色立绘文件存在绿色抠像底风险。当前 `BaseCombatant.gd` 只根据 alpha used rect 裁切，不会自动把绿色背景转成透明，因此角色运行图必须导出为真实透明 PNG。

文档与实际资源规格存在偏差，例如早期文档中的卡图、事件图尺寸与当前运行资源不一致。这会直接增加返工，应先更新为可执行资产契约。

## 视觉方向

整体采用三层视觉语言。

### 角色与卡图

角色是第一视觉锚点。风格以 Q 版或偏 SD 的二次元角色为主，强调清晰轮廓、夸张动作、阵营色和职业辨识。卡图可以使用较成熟的二次元插画，但卡牌窗口内必须主体集中，不烘焙文字、数值、边框、费用、稀有度或 UI 阴影。

四个角色链路暂定为：

| 阵营 | 关键词 | 视觉锚点 | 表现重点 |
| --- | --- | --- | --- |
| 红 | 拳击、爆发、近战 | 红黑白、拳套、冲击弧线 | 多段攻击、压迫、爆发 |
| 蓝 | 流动、抽弃、混沌回收 | 蓝白、卡片流、工具感 | 抽牌、弃牌、回收 |
| 绿 | 节奏、调律、腐蚀、成长 | 青绿、音符、藤蔓/能量波 | 延迟、复制、升级 |
| 橙 | 准备、背包、保留、消耗 | 橙白、装备、贴纸、道具 | 保留、抽到触发、消耗收益 |

### UI 与图标

UI 走明快模块化，不走厚重机械面板。基础规则：

1. 面板以白色和浅青色为主体，青蓝描边，深色文本。
2. 主操作按钮使用橙色或暖黄色强调，次级操作使用白底青边。
3. 阵营色只用于边框、徽记、选中光、标题条和少量状态强调，不把整屏染成单一色。
4. 图标使用粗轮廓、扁平色块和小尺寸可读结构，优先继承现有遗物图标方向。
5. 所有按钮、卡片、图标状态必须至少有 normal、hover/focus、pressed、disabled 四种视觉反馈。

### 世界与战斗舞台

世界观以轻机械浮岛和机器人遗迹为底，不把机器人写实细节作为全局 UI 主视觉。标题/选角的浮岛舞台语言应下放到战斗：战斗背景需要地面基线、远景层、敌我底座和低对比装饰，而不是只铺抽象浅色背景。

战斗舞台优先保证信息层级：

1. 玩家和敌人立绘清楚站在同一地面基线上。
2. 敌人意图、生命条、格挡和状态不被背景或立绘细节吞没。
3. 手牌区域和回合按钮保持最高操作可读性。
4. 背景中心战斗区低对比，边缘允许更多装饰。

## 低返工资产策略

### 资产契约先行

新增或更新资产规格文档，统一当前真实运行规格：

| 类型 | 运行规格 | 格式 | 关键验收 |
| --- | --- | --- | --- |
| 角色战斗立绘 | 高约 512-600，透明 PNG | RGBA PNG | 无绿底，脚底基线一致，缩到 200px 高仍清楚 |
| 角色头像 | 256x256 | RGBA PNG | 头像/半身，不用完整立绘硬缩 |
| 能量图标 | 128x128 或 16x16 内嵌版本 | RGBA PNG | 16px 下仍可辨认 |
| 卡牌插画 | 512x512 | RGBA PNG 或 JPG | 主体占 65%-80%，无文字无 UI |
| 事件插画 | 768x768 | PNG/JPG | 主体不贴边，右侧或下方留文字面板安全区 |
| 敌人战斗图 | 透明 PNG，按显示高度缩放 | RGBA PNG | 统一脚底/悬浮基线，不烘焙阴影 |
| 图标 | 128x128 或 64x64 | RGBA PNG | 32px 下可辨认 |
| 战斗背景 | 1200x700 或 2400x1400 | JPG/PNG | 中央低对比，底部手牌区不抢色 |

所有内容图必须生成 contact sheet：原尺寸、游戏显示尺寸、32px/64px 缩略图、深浅背景对照。未通过 contact sheet 的图不进入运行路径。

### 角色链路小批量生产

不要按资产类型横向推进“所有头像”“所有卡图”。改为按角色链路纵向推进：

1. 清理该角色战斗立绘透明通道和基线。
2. 统一头像、能量图标和选角背景。
3. 制作该角色共用卡图。
4. 制作 6-8 张最高频卡图。
5. 在战斗、选角、卡牌、奖励和图鉴里一次验收。

这样每轮都能获得可感知的完整角色体验，避免某一类资源大量完成但游戏内仍割裂。

### 敌人与事件接入

敌人首阶段不全量重画。先统一：

1. 战斗底座或软阴影。
2. 受击闪色和命中 VFX 挂点。
3. 敌人显示高度和悬浮/落地基线。
4. 高细节敌人与扁平图标的用途边界：战斗立绘使用完整敌人图，地图/图鉴小入口使用图标化版本。

事件图质量较高，首阶段不重画。通过事件界面遮罩、边缘柔化、白色文本板、背景降噪和安全区规则解决信息抢夺。

## UI 优化方案

### 全局主题

扩展现有 `themes/title_screen_theme.tres`、`themes/run_screen_theme.tres` 和 `themes/keyword_tooltip_theme.tres`，形成统一 token：

| Token | 用途 | 建议 |
| --- | --- | --- |
| `surface` | 主面板 | 白色 0.90-0.96 alpha |
| `surface_tint` | 弹层遮罩 | 浅青 0.65-0.75 alpha |
| `border` | 面板/按钮边 | 青蓝 |
| `primary` | 主操作 | 橙色 |
| `text` | 正文 | 深蓝黑 |
| `muted_text` | 次级文本 | 蓝灰 |
| `danger` | 不可用/负面 | 红橙 |
| `success` | 正面/获得 | 青绿 |

所有弹层改为同一结构：遮罩、主面板、标题条、内容区、底部操作区。优先做共用视觉，不改业务逻辑。

### 战斗 HUD

战斗 HUD 应靠近《杀戮尖塔》的阅读逻辑：

1. 顶部左侧：暂停、地图、牌库入口使用图标按钮，悬停/焦点有统一描边。
2. 顶部资源：金币和生命加入小图标或胶囊背景，避免纯文本飘在背景上。
3. 牌堆入口：能量、抽牌、弃牌、消耗堆固定在底部左右，显示数字徽章。
4. 回合按钮：右下角主操作，橙色主按钮，回合可结束时视觉权重高于其他按钮。
5. 选目标提示：减少纯大字提示，改为目标线、目标框和敌人意图处联动高亮。

### 卡牌模板

保留现有 144x184 外部尺寸和亮色模块结构。优化方向：

1. 增加阵营徽记或更清晰的阵营角标，但不新增必填数据字段。
2. 卡图区域统一裁切规则，避免人物脸部或动作被卡框截断。
3. 改善可打出/不可打出的差异：费用徽章、卡面明度、悬停反馈三处同时变化。
4. 继续使用星级表示稀有度，避免在类型栏塞文字。
5. 保持 `RichLabelAutoSizer` 控制文本，不允许描述覆盖星级或类型条。

### 弹层与流程界面

奖励、商店、牌库、地图、暂停、休息和事件对话按同一面板规范重皮肤。优先级如下：

1. 奖励和选牌：玩家高频看到，优先统一。
2. 商店和牌库：信息密度高，重点处理网格、价格、禁用态和返回按钮。
3. 地图：保持路线结构，强化当前可选节点和已走路径。
4. 事件对话：保留左图右文结构，但用插画遮罩和文本面板统一风格。
5. 暂停和设置：低频界面，复用通用弹层即可。

## 交互与动效方案

### 保留的交互契约

1. 手牌拖拽到目标释放。
2. 右键取消拖拽。
3. 悬停卡牌放大。
4. 目标需求卡牌显示轨迹线。
5. 无目标卡牌拖出即可释放。
6. 不可打出卡牌给出摇动和费用/卡面反馈。
7. 地图路线按层级推进。
8. 奖励、商店、牌库等弹层不改变业务流程。

### 强化的反馈

1. 拖拽线从简单曲线升级为带外发光和箭头端点的能量线，颜色随目标合法性切换。
2. 目标高亮从单纯边框升级为“边框 + 底座亮起 + 轻微缩放”，避免只在复杂敌图边缘显示。
3. 卡牌释放保留现有收束动画，但根据 `card_visual_profile` 调整释放目标和 VFX 类型。
4. 回合开始、回合结束、抽牌、弃牌、能量变化继续使用程序化反馈，避免额外出图。
5. 所有弹层出现和消失使用 0.12-0.22 秒短 Tween，不做长演出。

## 实施分期

### Phase 0：资产契约与止血

目标是减少后续出图返工。

1. 更新 `designer/ART_ASSET_GUIDE.md` 和相关资产流程文档，使规格与当前真实资源一致。
2. 增加角色透明通道检查和 contact sheet 检查流程。
3. 清理四个角色战斗立绘绿底，导出为真实透明 PNG。
4. 为缺图 fallback 建立类型化占位图，不再使用无语义默认图标。

验收：四个角色在战斗和选角中无绿色底；新规格文档不再与运行资源冲突；contact sheet 能看出 32px、64px 和游戏尺寸效果。

### Phase 1：全局 UI 外壳

目标是让界面先统一，不依赖新插画。

1. 统一主题 token、按钮、Tooltip 和基础面板。
2. 重皮肤奖励、商店、牌库、地图、暂停和事件对话弹层。
3. 顶部资源和底部牌堆入口改为统一图标胶囊。
4. 验证所有文字不越界、不被按钮裁切。

验收：不新增大量内容图的情况下，主要界面看起来属于同一 UI 系统。

### Phase 2：战斗舞台

目标是让战斗画面从“浅色 UI 背景”变成可读舞台。

1. 制作或复用 1 套 Act 1 战斗背景，包含低对比中央区、地面基线、远景机械/浮岛元素。
2. 为玩家和敌人增加统一底座/阴影。
3. 统一敌我生命条、格挡、状态和意图的层级。
4. 校验手牌、回合按钮和牌堆入口不被背景抢色。

验收：玩家、敌人、意图、手牌和回合按钮在一屏内层级清楚。

### Phase 3：角色链路

目标是逐个角色形成完整可感知风格。

每个角色一轮，推荐顺序：红、蓝、绿、橙。每轮包含：

1. 角色立绘透明通道和基线。
2. 角色头像和能量图标。
3. 角色共用卡图。
4. 6-8 张高频卡图。
5. 角色选角背景微调。
6. 该角色起始牌组和常见奖励场景视觉验收。

验收：玩家选择该角色进入战斗后，选角、立绘、卡图、能量图标和高频行为视觉一致。

### Phase 4：敌人与事件

目标是用较少重画统一内容密度。

1. 为现有敌人补统一底座、描边或展示处理。
2. 区分敌人战斗图和地图/图鉴图标用途。
3. 事件插画接入统一对话遮罩和文本面板。
4. 只对明显不合格的敌人或事件图做局部重画。

验收：高细节敌人和扁平图标不再混用在同一展示语境；事件界面图文信息不互相抢夺。

### Phase 5：表现库扩展

目标是用程序化反馈替代大量动效出图。

1. 扩展 `CardImpactVFX.gd` 的 VFX 预设到 8-12 个稳定类别。
2. 扩展 `CardPresentationResolver.gd` 的默认推断规则。
3. 为 attack、skill、power、status、heal、guard、draw、energy、item 建立 SFX/VFX 组合。
4. 用开发预览场景验证新增表现，不进入逐卡手工分支。

验收：新增卡牌只需配置数据字段即可获得可接受的表现反馈。

## 文件与系统边界

主要涉及：

- `designer/ART_ASSET_GUIDE.md`：资产规格和替换流程。
- `designer/ASSET_REPLACEMENT_GUIDE.md`：资产替换、验收、contact sheet 流程。
- `themes/title_screen_theme.tres`、`themes/run_screen_theme.tres`、`themes/keyword_tooltip_theme.tres`：全局 UI token 和控件状态。
- `scenes/Root.tscn`：战斗 HUD、弹层、地图和流程界面的视觉节点。
- `scenes/ui/Card.tscn`、`scripts/ui/Card.gd`：卡牌模板微调。
- `scripts/ui/Hand.gd`：拖拽线、目标高亮和不可用反馈微调。
- `scripts/ui/CombatFeedbackPresenter.gd`、`scripts/ui/CardPresentationResolver.gd`、`scripts/ui/vfx/CardImpactVFX.gd`：表现库扩展。
- `external/sprites/characters/`：角色链路资产。
- `external/sprites/ui/`：通用 UI、地图、标题、弹层和图标资产。

不修改：

- 卡牌动作脚本和战斗数值逻辑。
- 地图生成核心规则。
- 角色初始卡组和奖励逻辑，除非后续独立玩法需求要求调整。
- `FileLoader.gd` 的基本外部资源加载模式。

## 验收标准

1. 四个角色战斗立绘在选角和战斗里没有实色绿底或错误透明边。
2. 主要界面使用同一明亮 UI 外壳，按钮、弹层、Tooltip、奖励和商店的风格一致。
3. 战斗画面能在 1200x700 下清楚识别玩家、敌人、敌人意图、生命/格挡、状态、手牌、回合按钮和牌堆。
4. 卡牌拖拽、释放、取消、无效反馈和目标高亮仍保持现有交互契约。
5. 角色链路每轮验收必须覆盖选角、战斗、手牌、奖励、图鉴或牌库。
6. 所有新增图片必须通过真实游戏尺寸 contact sheet，而不是只看原图。
7. 新卡牌表现优先通过数据字段和程序化 VFX/SFX 获得，不新增逐卡硬编码。
8. 相关 Godot headless 回归通过，UI 布局测试不出现越界、重叠或缺失节点。

## 风险与应对

### 风格漂移

风险：角色、卡图、敌人和事件分别出图，最终像不同游戏。

应对：所有新图按角色链路或内容链路验收；每轮必须放进真实 UI 截图或 contact sheet，不只验收单张原图。

### 出图返工过高

风险：一次性要求全量卡图或全量敌人重画。

应对：优先 UI 外壳、透明通道、底座、遮罩和程序化反馈；内容图只处理高频、首屏和破坏观感的问题。

### UI 明亮但缺少战斗张力

风险：全局变浅后战斗像菜单背景。

应对：战斗舞台增加地面基线、远景层、敌我底座、命中反馈和暗部线条；背景中心区低对比，角色和敌人保持清晰轮廓。

### 交互被视觉改动破坏

风险：重皮肤弹层或 HUD 时改变按钮点击区域和手牌布局。

应对：优先改视觉节点、Theme 和 StyleBox；保留现有布局契约。每次修改后运行交互和布局回归。

## 推荐实施顺序

1. Phase 0：资产契约与角色绿底止血。
2. Phase 1：全局 UI 外壳统一。
3. Phase 2：战斗舞台统一。
4. Phase 3：按红、蓝、绿、橙逐个角色链路补齐。
5. Phase 4：敌人与事件接入。
6. Phase 5：表现库扩展。

该顺序的核心理由是：先统一“容器”和“验收规则”，再补内容图。这样每一次出图都能直接在稳定框架内验收，避免因 UI、裁切、背景和动效后改导致重复返工。
