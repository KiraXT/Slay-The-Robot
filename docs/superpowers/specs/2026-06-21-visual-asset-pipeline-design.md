# Slay the Robot 图片资产迭代方案

日期：2026-06-21

## 1. 目标

建立一套适合长期扩展的图片资产体系，覆盖角色、敌人、卡牌、事件、遗物、状态、消耗品、背景和边角 UI，并满足以下要求：

- 保留现有 JSON 数据驱动与外部 Mod 能力。
- 内容图片可以低成本替换，结构性 UI 不因内容换图而失效。
- 支持使用 GPT Image 2 批量生产，同时控制风格漂移和返工成本。
- 图片母版、运行图、提示词和配置来源职责清晰。
- 首阶段只处理静态图片，动画在后续迭代中单独设计。

## 2. 已确认的视觉方向

采用双层视觉体系：

- UI 外壳：废土丝网印刷。使用旧纸、粗墨线、工业警示色、铆钉、胶带和轻微错版效果。
- 内容插画：冒险卡通手绘。造型有趣但战斗有力度，允许幽默，也能表现 Boss、危险事件和机械损坏。

两层通过以下规则保持一致：

- 使用粗而略不规则的轮廓线。
- 使用有限色板和明确的阵营强调色。
- 控制纹理密度，保证 32px 至 96px 下仍可辨认。
- 插画不生成文字、数字、水印、卡框和按钮。
- UI 负责文字、数值、边框、稀有度和交互状态。

## 3. 当前工程现状

工程已经具备适合扩展的基础：

- `FileLoader.gd` 支持从 `external/` 加载并缓存外部图片。
- 角色、敌人、卡牌、遗物和事件图片大多由 JSON 路径配置。
- 角色已有战斗立绘、选角图标和卡牌描述能量图标三个字段。
- 事件已有事件背景字段和对话状态插画字段。
- 战斗背景按章节、地点、事件三级优先级选择。
- 当前内容规模约为 66 张卡、4 个角色、9 个敌人、22 个遗物和 9 个事件。

当前限制包括：

- 许多资产仍为空路径或使用 `icon.svg` 占位。
- 卡牌图片目前按 96×96 的单图使用，没有独立的插画、框架和稀有度装饰层。
- 结构性 UI 和外部内容资产的边界不够明确。
- 个别代码混用 Godot `load()` 与 `FileLoader.load_texture()`。
- `FileLoader` 缓存同一路径的图片，运行时覆盖文件后不会自动刷新。
- 缺图时通常返回空纹理，没有按资产类型显示明确的 fallback。

## 4. 选定架构：混合规范化

### 4.1 外部内容资产

以下资源放在 `external/sprites/`，由 Excel/JSON 记录路径，通过 `FileLoader` 加载：

- 角色和敌人立绘
- 角色选择头像
- 卡牌插画
- 事件插画与内容背景
- 章节、地点和战斗背景
- 遗物、状态、消耗品等内容图标

这些资产允许配置替换，并继续支持 Mod。

### 4.2 内部结构资产

以下资源放在 `res://assets/ui/`，由 Godot 场景、Theme 或内部资源直接引用：

- 卡牌底色、框架、稀有度装饰和状态覆盖层
- 面板、按钮、标签、分隔条和 NinePatch 资源
- 选中、悬停、禁用、受击等交互反馈
- 金币、锁、箭头等不会随内容对象变化的通用符号
- 各资产类型的缺图 fallback

这些资源与 UI 结构共同版本化，不通过内容表逐项配置。

### 4.3 加载边界

- `external/` 路径统一使用 `FileLoader.load_texture()`。
- `res://assets/ui/` 路径统一使用 Godot 内部资源引用或 `load()`。
- 不再把 `res://icon.svg` 作为发布内容的默认图片。
- 每类内容资产设置独立 fallback，缺图时保留明显但不阻断游戏的视觉提示。
- 开发模式后续增加清除图片缓存的入口；发布模式继续缓存。

## 5. 卡牌分层设计

卡牌是本次唯一需要结构升级的核心对象。推荐从后向前分为：

1. 底色层：角色或阵营颜色。
2. 插画层：每张卡独立的手绘卡通插画。
3. 框架层：卡牌类型和稀有度视觉。
4. 信息层：名称、类型、费用和描述文字。
5. 状态层：升级、发光、禁用、选中和拖拽反馈。

数据兼容策略：

- 新增语义明确的 `card_art_texture_path`。
- 读取时优先使用 `card_art_texture_path`，为空时回退到现有 `card_texture_path`。
- 现有 JSON 和 Mod 在兼容期内不需要立即迁移。
- 卡牌 Excel 和导表工具增加新列；完成迁移后旧字段标记为弃用，但首阶段不删除。

卡牌插画只提供画面内容，不包含名称、说明、费用、边框、稀有度和升级标识。

## 6. 目录和命名

运行图使用稳定的 `object_id` 命名，不使用中文名或显示名。

```text
external/sprites/
  characters/
    character_red/
      combat.png
      icon.png
      selection_background.jpg
  enemies/
    enemy_act_1_boss_1/
      combat.png
  cards/
    card_attack_basic/
      art.png
  events/
    event_pick_something/
      dialogue_state_pick_something_initial.jpg
      background.jpg
  backgrounds/
    acts/
      act_1.jpg
    locations/
  artifacts/
    artifact_draw_on_kill.png
  consumables/
  status_effects/

assets/ui/
  cards/
    backgrounds/
    frames/
    rarity/
    overlays/
  panels/
  buttons/
  icons/
  fallback/
```

母版和生产记录不随游戏发布：

```text
designer/art_source/
  style_bible/
  references/
  briefs/
  masters/
  contact_sheets/
```

母版文件较大时使用 Git LFS 或独立云盘管理；提示词、brief 和小型参考清单保留在仓库中。运行图继续由普通 Git 跟踪。

## 7. 图片规格

| 类型 | 建议母版 | 建议运行图 | 格式 | 关键规则 |
| --- | --- | --- | --- | --- |
| 卡牌插画 | 1024×1024 | 512×512 | PNG/JPG | 主体占 65%–80%，四周留 10% 安全区 |
| 角色/敌人 | 1024×1024 | 512×512 | 透明 PNG | 统一 3/4 视角和脚底基线，不烘焙投影 |
| 角色头像 | 512×512 | 256×256 | 透明 PNG | 头肩近景，64px 下可辨认 |
| 事件插画 | 1024×1024 | 768×768 | JPG/PNG | 主体偏左中，重要细节不贴边 |
| 战斗/章节背景 | 不低于 2400×1400 | 2400×1400 | JPG | 12:7，中心战斗区低对比 |
| 遗物/状态/消耗品 | 512×512 | 128×128 | 透明 PNG | 单物件、粗轮廓，检查 32px 和 64px |

通用规则：

- 使用 sRGB。
- 透明素材使用 PNG，完全不透明背景优先 JPG。
- 首阶段不引入 WebP，避免扩大现有加载和校验范围。
- UI 显示尺寸由场景决定，不直接等同于运行图像素。
- 图片内不烘焙文字和依赖具体 UI 布局的阴影。

## 8. Excel 与 JSON 维护规则

配置来源保持现有工作流：

- 卡牌、事件、遗物涉及的图片路径优先在对应 Excel 中维护。
- CSV/JSON 由 `external/tools/` 下的导表工具生成。
- 不将生成后的 JSON 作为长期手工维护源，避免下一次导表覆盖修改。
- 新增图片字段时，必须同步更新 Excel 列、转换工具、数据类和维护文档。
- 角色、敌人等当前没有对应工作簿的类型暂时继续维护 JSON；若后续纳入 Excel，再一次性迁移。

建议增加一份自动生成的资产清单，至少包含：

- `object_id`
- 资产类型
- 配置来源
- 运行图路径
- 目标尺寸和格式
- 当前状态：缺失、占位、待审、已批准
- 风格版本

## 9. GPT Image 2 生产流程

### 9.1 先制作风格验证包

首批只制作约 18 至 20 个代表性资产：

- 1 个角色：战斗立绘和头像
- 2 个敌人：普通敌人与 Boss
- 6 张卡：攻击、防御、能力各两张
- 1 个事件插画
- 约 8 个 UI 或内容图标

验证包必须在战斗、选角、事件和缩略图状态都通过后，才开始全量生产。

### 9.2 单项生产闭环

1. 为 `object_id` 编写 brief，描述对象、动作、玩法语义和构图。
2. 使用同一提示词模板生成 4 个候选。
3. 优先按轮廓和构图选择，不按大图细节选择。
4. 使用编辑迭代修正肢体、机械结构、配色和安全区。
5. 进行裁切、去底、缩放、压缩和格式转换。
6. 生成真实游戏尺寸 contact sheet。
7. 在游戏场景内完成最终验收。
8. 批准后导出到稳定运行路径，运行文件名不再随版本变化。

### 9.3 提示词模板

固定风格块示例：

```text
hand-drawn adventure cartoon illustration,
post-apocalyptic robot world,
bold uneven ink outlines,
screen-print inspired limited palette,
readable silhouette, expressive action,
subtle paper grain, controlled detail density
```

每项内容块包含：

- `subject`：对象和关键机械特征
- `action`：明确的动作与受力方向
- `camera`：近景、中景或统一 3/4 视角
- `palette accent`：角色或阵营强调色
- `mood`：幽默、紧张或危险
- `gameplay read`：攻击、防御、抽牌、弃牌等核心语义

固定约束块包含：

```text
no text, no letters, no numbers, no watermark,
no card frame, no UI elements,
safe margins, single focal point,
clean readable silhouette
```

为保证模型可替换，brief、提示词、参考图和后处理规则不得只存在于某次聊天记录中。

## 10. 验收与自动检查

### 10.1 自动检查

- 配置路径存在。
- 文件名与 `object_id` 规则一致。
- 尺寸、宽高比和格式符合资产类型要求。
- 声明为透明图的文件包含 alpha。
- 检测未引用文件、重复文件和仍在使用的 `icon.svg` 占位。
- Excel 导出结果中的图片字段与工作簿一致。

### 10.2 视觉检查

- 在 32px、64px 和 96px 下仍能识别。
- 角色和敌人的轮廓、视角、比例和脚底基线一致。
- 背景不干扰文字、意图图标和战斗主体。
- 不出现伪文字、额外肢体、断裂关节和错误机械透视。
- 同批卡图不重复使用相同构图。
- 颗粒和破损效果在小尺寸下不形成噪点。

### 10.3 游戏检查

- 战斗手牌、悬停、拖拽和升级状态。
- 选角界面、商店、奖励和地图缩略图。
- 事件插画和不同窗口宽高比。
- 缺图 fallback 是否明确但不影响继续游戏。
- 图片内存、加载时间和发布包体变化。

## 11. 推荐实施顺序

### 阶段 0：风格验证

- 完成 style bible、色板、线条和纹理规范。
- 制作并评审风格验证包。
- 确认 GPT Image 2 提示词模板和后处理规则。

### 阶段 1：工程基础

- 建立 `assets/ui/` 与新的 `external/sprites/` 目录边界。
- 卡牌改为插画、框架、信息和状态分层。
- 增加 `card_art_texture_path` 兼容读取。
- 清理 `load()` 与 `FileLoader` 的职责混用。
- 增加分类 fallback、缓存刷新和资产检查工具。
- 更新卡牌 Excel、导表工具和维护文档。

### 阶段 2：高频画面

- 红色角色及其头像。
- 常见敌人和第一章 Boss。
- 基础卡与代表性卡牌。
- 战斗背景和核心战斗 UI。

### 阶段 3：内容扩展

- 其余角色与卡池。
- 事件、遗物、状态、消耗品。
- 商店、奖励、地图和边角 UI。

### 阶段 4：统一润色

- 全局截图审查。
- 色板与线条粗细纠偏。
- 重复构图清理。
- 性能、内存和包体检查。

## 12. 非目标

本方案首阶段不包含：

- 骨骼动画或逐帧动画系统。
- 多套皮肤和完整资产 manifest/variant resolver。
- 多分辨率自动选择。
- 运行时下载图片。
- 让生成模型直接产出包含文字的完整卡牌或完整 UI 截图。

动画、多皮肤和更复杂的资源解析应在静态资产体系稳定后单独设计。

## 13. 完成标准

本方案进入全量生产前，应满足：

- 风格验证包已在游戏真实界面中通过评审。
- 卡牌分层方案不会破坏现有卡牌文本和交互。
- 旧 `card_texture_path` 内容和 Mod 仍可正常显示。
- 新增内容只需提供稳定图片路径，不需要修改 UI 场景。
- 卡牌和事件图片路径仍可从 Excel 正确导出到 JSON。
- 缺图、尺寸错误和未引用资产可以被自动发现。
- 运行图可以替换，母版和提示词可以追溯。
